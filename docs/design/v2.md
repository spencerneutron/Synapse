## Slice 1: retrieval quality

### Why

- **Filters are approximate.** `--type` and `--project` run after the vector
  search. v1.6.1 widens the search until enough rows pass, which works but
  scans more than needed and still ranks across the whole store.
- **Exact names miss.** Pure vector search is weak on identifiers: `#127`,
  `CloudKit`, file names, error codes.
- **Stale decisions surface.** A Decision note can name what it `supersedes`,
  but the old note stays `active`, so recall keeps offering the replaced
  choice.

### What changes

1. **Store schema v2** (a `meta` table records `schema_version`):
   - `chunks` gains `status` (`active` | `superseded`), `superseded_by`, and
     two nullable provenance columns reserved for sharing, `origin` (which
     store wrote the chunk) and `author`. That avoids a second migration when
     slice E lands.
   - `chunks_vec` becomes `vec0(embedding float[768] distance_metric=cosine,
     project text partition key, source_type text, status text)`. Filters run
     inside the vector search, so they are exact. Searches without a project
     filter still span every partition (verified on sqlite-vec 0.1.9).
   - `chunks_fts`, an FTS5 table over chunk text (`porter unicode61`
     tokenizer, available in the bundled SQLite 3.53).
2. **Upgrade without re-embedding.** `synapse extract upgrade` first copies
   `vectors.db` to `vectors.db.bak-<date>`, then rebuilds `chunks_vec` from
   the stored vectors, builds the FTS index, and sets the schema version. It
   is idempotent. Other commands that see a v1 schema stop and point to it.
   `synapse setup` runs it.
3. **Hybrid recall.** The vector search and an FTS5 BM25 search both run
   with the same filters. Results merge by reciprocal rank fusion (k = 60).
   Output keeps the cosine score for vector matches, so the skill's
   "above ~0.55 is strong" guidance still holds, and labels each hit
   `vector`, `keyword`, or `both`. `--mode vector|keyword|hybrid` defaults to
   hybrid. The v1.6.1 widening loop now serves only `--since`, the one filter
   that still runs after the search.
4. **Supersession.** When `/synapse:extract-session` writes a Decision with
   `supersedes`, it then runs `synapse extract supersede <old note> --by
   <new note>`. That marks the old note's chunks `superseded` in place
   (verified: sqlite-vec updates metadata without re-inserting vectors) and
   sets `status: superseded` and `superseded_by` in the old note's front
   matter (it needs the store's `vault_path`, or the note's full path; it never
   calls the Obsidian CLI). The DB is the authority: a re-embed cannot revive a
   superseded note. Recall hides superseded chunks unless
   `--include-superseded` is passed, and then labels them.
5. **Recall golden set (measurement without agent runs).** `synapse
   recall-check <file>` runs a list of queries with their expected sources and
   reports hit rate at 5 and mean reciprocal rank. The golden file for your
   store stays in the store (it quotes your sessions); CI runs a synthetic
   fixture with a deterministic fake embedder, so no Ollama is needed there.
   Baseline before the upgrade, compare after.

### Done when

- The golden set scores at least as well after the upgrade as before, and the
  exact-identifier queries in it improve.
- A filtered query costs one vector search, not a widening loop.
- A superseded decision stops appearing in default recall and appears,
  labeled, with `--include-superseded`.
- The upgrade leaves a backup, is idempotent, and changes no vector.
- Tests cover fusion, filters, supersession, and the upgrade on the fixture
  store; CI stays green on macOS, Linux, and Windows.

### Results (2026-10-26, the author's store: 1,580 chunks, 2 projects)

Measured on a copy of the store with a 24-case golden set: 8 identifier
cases whose answers came from a text search of the chunks, 12 paraphrased
concept questions, and 4 filtered queries.

| Group | Baseline (v1.6.1, vector) | Slice 1 (hybrid) |
|-------|---------------------------|------------------|
| Overall hit@5 / MRR | 0.833 / 0.792 | **1.000 / 0.910** |
| Identifier | 0.625 / 0.562 | **1.000 / 0.875** |
| Filtered | 0.750 / 0.750 | **1.000 / 1.000** |
| Concept | 1.000 / 0.958 | 1.000 / 0.903 |

- Every baseline miss is now found. The filtered miss was a real bug:
  notes tagged `veilmx` were invisible to `--project VeilMX`.
- One concept question fell from rank 1 to 3 (still a hit). Fusion favors a
  chunk both searches rank moderately over one only the vector search ranks
  first. Weighting the keyword list at 0.3–0.7 restored concept MRR to 0.958
  but lost two identifier hits, so plain equal-weight fusion stays.
- Vector-only mode on the new schema matched the baseline's concept scores
  exactly; the gains come from the keyword index and the exact filters.
- The upgrade rebuilt 1,580 chunks with every vector byte-identical, kept a
  backup, and was a no-op on re-run. Supersession was exercised on a real
  near-duplicate decision pair.
- Supersession itself moved the needle: once that pair's older decision was
  superseded, the DKIM question rose from rank 3 to 2 (concept MRR 0.917,
  overall 0.917), because the stale near-duplicate no longer competed.

## Sharing requirements (small team), for slice E

Captured now so slices B–D do not paint E into a corner.

- **Scrub gate.** Before anything leaves a personal store: generalize
  session-local references (bare `#17`, "Wave B", "yesterday's session"),
  replace paths and machine ids with placeholders, and scan for secrets.
  Judgment in extraction, plus a deterministic pass and a lint in the share
  step.
- **Review to share.** Sharing is opt-in per note, never automatic.
- **Provenance.** Every shared chunk carries `origin` and `author` (reserved
  in schema v2), so readers can weigh it and a bad entry can be traced and
  pulled.
- **Local wins.** A member's own store outranks the shared one on conflict;
  shared hits are labeled in recall.
- **Transport, to decide in E.** Because archives are canonical and indexes
  are rebuildable, a git repository of scrubbed notes and archives, with each
  member rebuilding the index locally, may beat a server. An MCP server (F)
  stays the option for clients outside Claude Code.
